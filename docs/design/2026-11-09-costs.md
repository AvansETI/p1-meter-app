## 1. Goal

Show a household what its energy costs: today so far (Live), per bucket and per period with a
comparison (History), and a forecast for the calendar year. Supports single-tariff, double-tariff
(normal/off-peak) and dynamic (quarter-hour) contracts, net metering until 2026 and the regime
without net metering from 2027.

Out of scope: comparing contracts or suppliers, invoices/payments, CSV export.

## 2. Tariff model

Tariffs are stored per household (signature) as a list of **tariff periods**, each valid from a
date until the next one starts. Amounts are in euros; "incl." means including energy tax and VAT,
as on a Dutch annual statement.

```ts
TariffPeriod = {
  validFrom: 'YYYY-MM-DD';
  electricity:
    | { type: 'single'; perKwh: number }                          // incl.
    | { type: 'double'; normalPerKwh: number; offPeakPerKwh: number } // incl.
    | { type: 'dynamic'; markupPerKwh: number; energyTaxPerKwh: number; vatPercent: number };
      // dynamic: price = (quarter-hour day-ahead price + markup + energy tax) × (1 + VAT)
  export: {
    compensationPerKwh: number;   // feed-in compensation (excess under net metering; all export from 2027)
    feePerKwh: number;            // feed-in costs charged by the supplier (from 2027)
    dynamicMarkupPerKwh?: number; // dynamic: export earns day-ahead price + this (may be negative)
  };
  gas?:
    | { type: 'fixed'; perM3: number }                            // incl.
    | { type: 'dynamic'; markupPerM3: number; energyTaxPerM3: number; vatPercent: number };
  fixed: {
    supplierPerMonth: number;     // vastrecht leverancier (electricity + gas), incl.
    gridPerMonth: number;         // netbeheerkosten (electricity + gas), incl.
  };
  taxReductionPerYear: number;    // heffingskorting, incl. VAT, as a positive amount
}
```

Validation: amounts ≥ 0 except markups (may be negative); VAT 0–100 %; `validFrom` unique;
periods sorted by date. Days before the first period have **no costs** (shown as "–").

## 3. Rules

### 3.1 Bands for double tariffs

The kit only forwards the total counters (no T1/T2 split), so the band is derived from time:
**off-peak** = Monday–Friday 23:00–07:00 and all of Saturday and Sunday (local time); otherwise
**normal**. Usage per quarter hour is assigned to the band of that quarter hour. National
holidays are not treated as off-peak (grid operators differ); a known approximation.

### 3.2 Usage per quarter hour

Import, export and gas per 15-minute interval from the counters at the quarter boundaries
(`aggregateWindow(every: 15m, fn: last)`, deltas like the history buckets, gaps excluded).
Gas counters update every 5 minutes or hourly; for dynamic gas only the daily total matters.

### 3.3 Electricity costs from 1-1-2027 (no net metering)

Per quarter hour:

- import × price (single/double band, or dynamic: `(dayAhead + markup + energyTax) × (1+VAT)`)
- − export × compensation (single/double), or export × `(dayAhead + dynamicMarkup)` (dynamic)
- - export × feed-in fee

### 3.4 Electricity costs until 31-12-2026 (net metering), per calendar year

Export cancels import for as long as the year's cumulative import exceeds cumulative export:

- **Single tariff**: netted kWh cost nothing; per quarter hour `(import − export) × price` while
  the running year balance (import − export) stays ≥ 0. Once export exceeds import for the year,
  the excess earns `compensationPerKwh`.
- **Double tariff**: like single, but with two running balances: normal against normal and
  off-peak against off-peak first; a remaining surplus in one band nets against the other band's
  deficit at the end of the year (shown in the year totals; per-bucket values use the band
  balances).
- **Dynamic**: the **supply part** is not netted — import costs `dayAhead + markup`, export earns
  `dayAhead + dynamicMarkup` per quarter hour (excl. VAT). The **energy tax and VAT** are netted:
  energy tax is charged on `max(0, yearImport − yearExport)` kWh, VAT over the supply part plus
  that tax. Per bucket the tax part is shown with the running balance as for single tariffs.

Because net metering is settled per year, a bucket's cost is "as far as known now": with a running
balance that becomes negative later in the year, earlier buckets do not change retroactively.

### 3.5 Gas, fixed costs and tax reduction

- Gas: m³ × fixed price, or dynamic `(dayPrice + markup + energyTax) × (1+VAT)` per day.
- Fixed costs per day = (supplier + grid per month) / days in that month.
- Tax reduction per day = taxReductionPerYear / days in that year (subtracted).
- A bucket's **total cost** = electricity + gas + fixed − tax reduction (for hour buckets the
  fixed costs and reduction are spread per hour).

## 4. Prices

### 4.1 Sources

| Data                     | Source                                                       | Resolution                            | Notes                         |
| ------------------------ | ------------------------------------------------------------ | ------------------------------------- | ----------------------------- |
| Electricity day-ahead NL | ENTSO-E Transparency Platform (A44, area `10YNL----------L`) | 15 min since 1-10-2025, 60 min before | free API key (`ENTSOE_TOKEN`) |
| Gas day price            | EnergyZero public API (`usageType=3`)                        | day                                   | excl. VAT and tax             |

Prices are stored **excluding VAT and taxes** in EUR per kWh / per m³.

### 4.2 Storage (InfluxDB, separate bucket)

Bucket `energy-prices` (created by the product owner, read/write token only for this bucket):

| Measurement             | Tags                                 | Field         | Time              |
| ----------------------- | ------------------------------------ | ------------- | ----------------- |
| `electricity_day_ahead` | `area=NL`, `resolution=PT15M\|PT60M` | `eur_per_kwh` | interval start    |
| `gas_day_ahead`         | `area=NL`                            | `eur_per_m3`  | day start (local) |

### 4.3 Ingestion

A price job in the API process (one instance):

- every day at 13:15 and 15:00 local (day-ahead results are published ~12:45–13:00) fetch
  tomorrow; at start-up and every hour fill any missing days of the last 7 days;
- one-time **backfill** from 2023-08-01 (first data) in monthly chunks, rate-limited;
- idempotent writes (same timestamp overwrites); failures logged, retried on the next run.

## 5. Tariff storage (SQLite on the server)

- Built-in `node:sqlite` (no native dependency), file `/var/lib/p1-meter-app/p1.db`
  (systemd `StateDirectory=p1-meter-app`, owned by `p1meter`, survives deploys and rollbacks).
- Tables:
  - `tariff_sets(signature PRIMARY KEY, periods JSON, version INTEGER, updated_at)`
  - `tariff_versions(signature, version, periods JSON, created_at, client_ip_hash)` — every save
    keeps the previous set; the UI can restore any version (undo vandalism or mistakes).
  - `daily_costs(signature, day, tariff_version, json)` — cache of computed daily costs
    (§6.2), invalidated when the tariffs change.
- Migrations: numbered SQL files applied at start-up in a transaction.
- Backup: daily `VACUUM INTO /var/lib/p1-meter-app/backups/p1-YYYY-MM-DD.db`, 14 kept.
- Editing: anyone with a valid session may save (product owner decision); writes are
  rate-limited (10/hour per household) and logged with masked signature.

## 6. API

### 6.1 Endpoints (session required)

| Route                                      | Purpose                                                                    |
| ------------------------------------------ | -------------------------------------------------------------------------- |
| `GET /api/v1/tariffs`                      | current tariff periods + version                                           |
| `PUT /api/v1/tariffs`                      | save periods (optimistic: `If-Match: <version>`, `409` on conflict)        |
| `GET /api/v1/tariffs/versions`             | earlier versions (date, number of periods)                                 |
| `POST /api/v1/tariffs/versions/:n/restore` | restore a version (creates a new version)                                  |
| `GET /api/v1/live/today` (extended)        | `costs: { totalEur, electricityEur, gasEur, fixedEur }` when tariffs exist |
| `GET /api/v1/history` (extended)           | `costEur` per bucket, `costs` in totals and previous                       |
| `GET /api/v1/costs/forecast?year=YYYY`     | forecast for a calendar year                                               |

### 6.2 Calculation

- Cost engine as pure functions in `apps/api/src/costs/` (fully unit-tested), input: usage per
  quarter hour, prices, tariff periods, year-to-date netting balances.
- Daily costs are computed from quarter-hour usage and prices (one Flux query per day range,
  joining usage and prices) and cached in `daily_costs`; weeks, months and years sum days.
  Day views (hourly buckets) are computed directly.
- Net metering needs the running balance since 1 January: taken from the cached days of that year.

### 6.3 Forecast

`actual cost year-to-date + expected rest`: for the remaining days, the cost of the same days last
year (if available and complete), otherwise the average daily cost of the last 30 days. Shown with
"o.b.v. verbruik vorig jaar" or "o.b.v. de afgelopen 30 dagen".
